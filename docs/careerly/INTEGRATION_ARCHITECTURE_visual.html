Careerly Backend × Job Matching Agent 整合架构审计

可视化指南 2026-09-30 work_agent + careerly
审计推翻了任务书里的一个核心前提：不存在「两个项目需要整合」。 Careerly 的后端层早已长在 work_agent 仓库内部，Agent 适配层也在位。 真正要做的不是「合并」或「重建适配层」，而是收敛边界、补齐缺口、把端到端跑通。

1三层架构：已物理共存于单仓库

一个 FastAPI 进程，三个逻辑层，两个独立数据库。不需要第二套服务。

关键点：L2 → L1 是进程内方法调用，不是 HTTP。不要为了方便把引擎拆成独立服务 —— 同一进程内再走一次 HTTP 往返，只增加延迟和故障面。

2八项缺口：真正要动手的地方

按严重度分级。三项阻断必须先修，其余按路线推进。

G3 最易被低估：Careerly 的核心表达是「看见成长」，而成长 = 相邻两次能力快照的 diff。 当前 capability_snapshot 只是 analysis_results 的一个 JSON 列， 没有跨项目的时间序列，产品就只剩「一次分析」，长不出「成长」这条线。

3双库边界：过程 vs 结果

一个可丢弃，一个必须备份。判据比文档更管用。

G2 的根因就在这张图里：graph_state.db 没有 user_id， 引擎不知道「谁」在分析。于是只要拿到 session_id，就能读到他人的匹配结果与简历片段。

4实施路线：P0 做完才有意义

P0 是唯一「不做就无法验证任何东西」的阶段，必须最先执行。

P0–P2 是关键路径（琥珀色）：先能连通，再能观测，然后才有成长。P3–P5 属于锦上添花，不能抢占 P0。

6三条不可破的边界

  • Flutter 只认识 Careerly API。永不直接调 /api/v1/match。LangGraph、Qwen、Playwright、爬虫对 App 完全不可见。
  • L2 → L1 是进程内方法调用，不是 HTTP。绝不为引擎单独起一个 FastAPI 服务 —— 同一进程内再走一次 HTTP 往返，只增加延迟与故障面。
  • Careerly 领域模型 ≠ 引擎领域模型。两者只能通过显式映射函数互转。禁止把 MatchResult 直接变成 API 响应，也禁止让 JobPosting 落进 careerly.db。
